# Инструменты анализа производительности

## Краткий ответ (30 секунд)

По задачам: **Lighthouse / PageSpeed Insights** — аудит, оценки и подсказки по FCP/LCP/CLS/TBT (PSI ещё и реальные данные CrUX); **Performance** (DevTools) — запись и профиль кадра: что ест main thread, длинные задачи, layout, paint, GC; **Network** — тайминги запросов, размеры, кэш, waterfall; **Coverage** — сколько CSS/JS не используется; **Memory** — снимки кучи и утечки; **Rendering** — paint flashing, layer borders, layout shifts; **React DevTools Profiler** — какие компоненты рендерились и почему; **web-vitals/`PerformanceObserver`** — реальные метрики пользователей. Порядок: измерить → найти узкое место → оптимизировать → переизмерить.

## Подробно

### Chrome DevTools

**Performance**
- Запись сценария: загрузка, взаимодействие, скролл.
- Main thread: `Task`, `Function Call`, `Layout`, `Recalculate Style`, `Paint`, `Composite Layers`, `GC`.
- Длинные задачи (> 50 мс) — главный враг INP.
- `Bottom-Up` / `Call Tree` — кто именно занял время; `Flame Chart` — хронология.
- `Layers` (старая панель) / современный рендеринг — какие слои созданы.

**Network**
- Waterfall: DNS, начальное соединение, TLS, TTFB, download.
- Размеры (gzip/br), приоритеты, статусы, инициатор.
- Условия: «Slow 4G», «CPU ×4», offline.

**Coverage** (в Command Menu → Show Coverage)
- Сколько JS/CSS из файлов реально выполнилось. Обычно 60–80% библиотек не используется на первой загрузке → кандидат на code-splitting.

**Memory**
- Heap snapshot → сравнение двух снимков → удерживаемые объекты.
- Allocation instrumentation on timeline — кто аллоцирует.
- Performance monitor — live CPU/JS heap/DOM nodes/listeners.

**Rendering**
- Paint flashing (что перерисовывается);
- Layer borders;
- Layout Shift Regions (CLS);
- FPS meter.

**Application**
- Storage (cookies, local/session/IndexedDB/CacheStorage), Service Workers, Manifest, clear site data.

**Sources**
- Breakpoints, Conditional, Event Listener Breakpoints, blackboxing для библиотек.

### Lighthouse / PageSpeed Insights

- **Lighthouse**: локально/в CI (`lighthouse-ci`) — FCP, LCP, TBT, CLS, Speed Index, SEO, a11y, best practices.
- **PageSpeed Insights**: лабораторные и **полевые** данные CrUX (28 дней).
- **Search Console → Core Web Vitals**: реальные данные Google для индексируемых страниц.

Ограничения: Lighthouse — синтетика на одном устройстве; не отражает вашу аудиторию. Поэтому важно смотреть PSI/CrUX и `web-vitals`.

### RUM: реальные пользователи

```js
import { onLCP, onINP, onCLS } from "web-vitals";
```

- Сбор через `PerformanceObserver` (`largest-contentful-paint`, `layout-shift`, `event`).
- Сегментация: мобильные/десктоп, страна, тип соединения.
- `navigator.connection.effectiveType` для условий.

### Другие инструменты

| Инструмент | Для чего |
|---|---|
| `web.dev Measure` / `pagespeed.web.dev` | быстрая оценка |
| WebPageTest | мультидевайс, видео-сравнение |
| Sentry/Datadog RUM | продовые ошибки и метрики |
| `why-did-you-render` | лишние ререндеры React |
| React DevTools Profiler | рендеры и причины (Highlight updates) |
| Bundle Analyzer (`vite-bundle-visualizer`, `source-map-explorer`) | вес бандла |
| Node `--prof`, `0x`, Clinic.js | серверный JS |

### Что отвечать про методику

1. Зафиксировать гипотезу и метрику.
2. Снять **профиль** (Performance), а не просто оценку Lighthouse.
3. Найти длинную задачу/тяжёлый ресурс.
4. Поменять и сравнить (Performance → сравнение записей; PSI — повторно).
5. Проверить влияние на другие метрики (улучшил LCP — не испортил INP).

> [!warning] Типичная ошибка ответа
> «Запускаю Lighthouse и получаю 100». На собеседовании важнее показать, что умеете читать **Performance** (флейм-чарт, длинные задачи) и знаете, что Lighthouse — синтетика.
