# Оптимизация приложения и метрики

## Краткий ответ (30 секунд)

Оптимизируют по трём осям: **загрузка**, **отзывчивость**, **визуальная стабильность**. Core Web Vitals: **LCP** (когда виден главный контент, ≤ 2.5 с), **INP** (задержка от взаимодействия до отрисовки, ≤ 200 мс; с марта 2024 заменил FID), **CLS** (сдвиги, ≤ 0.1). Вспомогательные: TTFB, FCP, TBT, Speed Index. Метрики снимают в **поле** (реальные пользователи, CrUX/`web-vitals`) и в **лаборатории** (Lighthouse/DevTools). Улучшения: меньше JS, критичный CSS, `preload`/`preconnect`, `loading="lazy"`, разделение бандла, кэширование, сжатие (brotli), статическая генерация, вынос тяжёлого JS в Worker.

## Подробно

### Core Web Vitals (пороги на 75-м процентиле)

| Метрика | Что измеряет | Хорошо | Плохо |
|---|---|---|---|
| **LCP** | отрисовка самого крупного элемента | ≤ 2.5 с | > 4 с |
| **INP** | взаимодействие → следующий paint | ≤ 200 мс | > 500 мс |
| **CLS** | сумма непредвиденных сдвигов | ≤ 0.1 | > 0.25 |

- **FID** — устарел (заменён INP в марте 2024). Инструменты вроде Lighthouse могут ещё показывать его как лабораторный TBT.
- **TTFB** — время до первого байта; серверная/CDN/кэш-часть LCP.
- **FCP** — первая отрисовка текста/картинки. Не входит в Core Web Vitals, но важен.
- **TBT** — суммарное время блокировки (лабораторная замена INP).
- Для SPA: LCP считается для начальной навигации; для «переходов» без перезагрузки — не считать через CWV-поля.

### Почему именно 75-й процентиль

Google в Search и CrUX смотрит на 75-й перцентиль визитов на страницу: порог должен быть «хорошим» хотя бы для 75% пользователей (мобильные и десктоп отдельно). Один перцентиль — мера, а не среднее: единичные «медленные» визиты не тянут сайт на дно.

### Архитектурные меры

**Загрузка:**
- SSR/SSG/ISR (Next/Astro), стриминг HTML.
- Критический CSS inline, остальное — асинхронно.
- `preload` для LCP-картинки/шрифта; `preconnect` к критичным origin; `dns-prefetch`.
- Картинки: AVIF/WebP, `srcset`/`sizes`, `width`/`height`, `fetchpriority="high"` для LCP-картинки.
- Кэш: `Cache-Control: immutable` для хешированных бандлов, CDN, Brotli.
- Код-сплиттинг роутов, `React.lazy`/`dynamic import`, tree-shaking, отказ от moment/lodash целиком.

**Отзывчивость:**
- Меньше JS на главном потоке; длинные задачи (> 50 мс) дробить — `scheduler.yield`/`isInputPending`.
- Тяжёлый парсинг/дедупликация — Web Worker.
- Не блокировать обработчики синхронной работой; большие списки — виртуализация.
- `INP`: defer неключевых обработчиков, `startTransition` в React, не мерцать вводом.

**Стабильность:**
- Явные размеры у изображений/iframe/видео.
- `font-display: swap`, `size-adjust` для шрифтов.
- Не вставлять баннеры над контентом; не анимировать `top/left`.

### Что показывать в ответе

1. **Измерение.** Сначала — Lighthouse/PSI + CrUX, потом работа.
2. **Гипотеза и метрика.** «LCP 3.1 с, 40% причин — картинка-герой. Добавили preload + AVIF → 2.2 с».
3. **Стоимость.** Что выбрали и почему — не «всё сразу».
4. **Проверка в поле.** `web-vitals` + аналитика; смотреть 75-й перцентиль и мобильные.

### Код для снятия метрик

```js
import { onLCP, onINP, onCLS } from "web-vitals";

const send = (metric) => navigator.sendBeacon("/analytics", JSON.stringify(metric));
onLCP(send);
onINP(send);
onCLS(send);
```

`sendBeacon` — чтобы не терять данные при уходе со страницы.

> [!tip] Если спросят про FCP
> «FCP — досягаемая метрика первого текста. Для неё критичны CSS, шрифты и блокирующий JS. Но запись в Core Web Vitals — LCP/INP/CLS».
