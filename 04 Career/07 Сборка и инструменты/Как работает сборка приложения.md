# Как работает сборка приложения

## Краткий ответ (30 секунд)

Бандлер проходит **граф модулей**: находит точку входа → читает импорты → резолвит пути (алиасы, `node_modules`) → применяет **трансформации** (TS, JSX, CSS, постпроцессоры) → собирает граф → **оптимизирует** (tree-shaking, минификация, code splitting, хеши в именах) → отдаёт ассеты. Dev-режим — без минификации и с HMR; prod — минификация, хеширование для долгого кэша, split по маршрутам. Глобально: **resolve → load → transform → bundle → optimize → emit**.

## Подробно

### Этапы

1. **Entry** — `index.js`/`main.tsx`.
2. **Resolve** — превратить `import "./Button"` в путь: расширения, алиасы (`@/`), `exports` из `package.json`, browser-поля.
3. **Load** — прочитать файл (или получить по HTTP).
4. **Transform** — TS → JS, JSX → `jsx()`, SCSS → CSS, autoprefixer, полифилы по `browserslist`.
5. **Analyze** — найти `import`/`export`/`import()`; построить граф.
6. **Tree-shaking** — выкинуть неиспользуемые экспорты (зависит от side-effects).
7. **Code splitting** — общие чанки, динамические импорты.
8. **Minify** — terser/esbuild/oxc; CSS — lightningcss.
9. **Hash** — `app.3f2a1b.js` для долгого кэша.
10. **Emit** — записать в `dist/`, сгенерировать `index.html` со ссылками.

### Tree-shaking

```js
// library
export function a() {}
export function b() {}

// app
import { a } from "library";
```

- Работает только с **ESM** и статическими импортами.
- `"sideEffects": false` в `package.json` библиотеки — разрешает удалять «неиспользованные» модули.
- Импорт barrel-файла (`import { Button } from "ui-kit"` где `export *`) может тянуть всё, если нет sideEffects.

### Side effects

```js
// побочный эффект — глобальный полифил
import "core-js/stable";
```

Такое нельзя выкинуть. `sideEffects: false` — обещание библиотеки, что «неиспользуемое» безопасно удалять.

### Code splitting

- **Точки входа** (multi-page).
- **Динамические импорты** `import()`.
- **Общие чанки** — `manualChunks` (webpack) / `advancedChunks` (Vite 8/Rolldown).
- **Vendor-чанк** — выносить стабильные зависимости для кэша.

### Dev-сервер против prod

| | Dev | Prod |
|---|---|---|
| Трансформации | on-demand | весь граф |
| Минификация | нет | да |
| HMR | да | нет |
| Полифилы | по need | по `browserslist`/`target` |
| Source maps | inline/eval | external, скрытые |
| Хеши | нет | да |

### `package.json` поля

- `main` (CJS), `module` (ESM), `browser`, `exports` (современный условный экспорт), `types`.
- `browserslist` — какие браузеры поддерживаем; влияет на трансформации и полифилы.

### Хеши и кэш

- Имя файла с хешем → `Cache-Control: immutable`.
- `index.html` — без долгого кэша (ссылается на новые хеши).
- `integrity`/SRI — если нужно.

### Анализ бандла

- `vite-bundle-visualizer`, `webpack-bundle-analyzer`, `source-map-explorer`.
- Смотреть: размер, дубли зависимостей (две версии lodash), неиспользуемые части.

> [!tip] Как отвечать
> «Бандлер строит граф модулей от entry: resolve → transform → analyze → tree-shake → split → minify → emit с хешами. Dev-режим ленивый и с HMR, prod — полный граф и оптимизации. Tree-shaking требует ESM и `sideEffects`».
