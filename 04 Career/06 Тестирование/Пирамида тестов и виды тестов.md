# Пирамида тестов и виды тестов

## Краткий ответ (30 секунд)

**Пирамида**: много **юнит-тестов** (чистые функции, хуки, утилиты — быстрые, дешёвые), меньше **интеграционных/компонентных** (несколько модулей/компонент с эмуляцией сети), ещё меньше **e2e** (браузер, весь стек — дорого и flaky). Альтернатива — **«trophy»** (Kent C. Dodds): мало юнитов, максимум интеграционных, немного e2e. Плюс **статические проверки** (TypeScript, ESLint) — самый дешёвый уровень. Главное — тестировать **поведение**, а не реализацию: «пользователь видит/делает», а не «вызвался ли внутренний метод».

## Подробно

### Уровни

| Уровень | Что тестирует | Скорость | Стоимость | Инструменты |
|---|---|---|---|---|
| Static | типы, линт, форматирование | мгновенно | низкая | TypeScript, ESLint, Prettier |
| Unit | одна функция/класс/хук | миллисекунды | низкая | Vitest/Jest |
| Component | компонент с DOM | десятки мс | средняя | Testing Library + jsdom/browser |
| Integration | фича с API/стором | сотни мс | средняя | RTL + MSW |
| E2E | полный сценарий | секунды–минуты | высокая | Playwright, Cypress |
| Visual | внешний вид | секунды | средняя | Playwright `toHaveScreenshot`, Vitest Browser |

### Что тестировать

- **Бизнес-логику** (валюта, даты, цены, права) — юнит.
- **Граничные случаи** (пустые данные, ошибки, медленная сеть) — юнит/интеграция.
- **Пользовательские сценарии** (вход, оформление заказа) — e2e.
- **Поведение компонента** (валидация, disabled, сообщения) — Testing Library.
- **Критичные интеграции** (оплата, авторизация) — e2e.

### Что НЕ тестировать

- Реализацию (state names, приватные методы, количество рендеров) — тесты ломаются при рефакторинге.
- Сторонние библиотеки (уже протестированы).
- Всё подряд ради покрытия — «тест ради теста».

### Покрытие

- 100% **не** означает качество: можно покрыть каждую строку, но не проверить ошибки.
- Полезно как **сигнал**: низкое покрытие в критичном модуле — повод добавить тесты.
- Не гнаться за цифрой в отчёте.

### Пирамида vs trophy

```
        e2e          e2e
      integration      (мало)
        unit        integration (много)
                    unit (немного)
   пирамида          trophy
```

Для фронтенда «trophy» практичнее: компоненты лучше тестировать с DOM и пользователем, а не мокать каждый хук.

### Сигналы плохих тестов

- Тесты падают при изменении стилей/DOM-структуры.
- «Sleep» вместо ожидания.
- Мок на моке (мокают всё).
- Тесты не проверяют ошибки и границы.
- Большие снапшоты без ревью.

> [!tip] Как отвечать
> «Пирамида — про стоимость. Логику — юнитами, компонент — Testing Library по поведению, путь пользователя — e2e. Типы и линтер — первый уровень. Покрытие смотрю как сигнал, а не цель».
