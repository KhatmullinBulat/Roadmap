# Сборщик мусора и достижимость

## Краткий ответ (30 секунд)

GC в JavaScript управляется **автоматически** и не даёт освободить память вручную (`delete` удаляет свойство, но не освобождает объект). Ключевое понятие — **достижимость**: объект жив, если до него можно добраться от корней (глобальный объект, стек вызовов, замыкания, DOM, регистр). В современных движках используется **mark-and-sweep**: обойти достижимые объекты (marks), освободить остальные (sweep), плюс **tri-color marking** для инкрементальности и **weak references** (`WeakMap`, `WeakRef`, `FinalizationRegistry`) для слабых связей. **Reference counting** в JS не используется.

## Подробно

### Доступность → достижимость

- **Корни**: `globalThis`/`window`, стек вызовов, локальные переменные, замыкания, активные обработчики, промисы.
- Объект достижим, если есть **цепочка ссылок** от корней.
- Циклические ссылки **не проблема** для mark-and-sweep: если к циклу нет пути от корней, он весь как недостижимый попадает в сборку. Это главное отличие от reference counting (как в CPython или старой IE).

```js
function leak() {
  const big = new Array(1e6).fill("x");
  window.onresize = () => console.log(big.length); // big живёт, пока жив обработчик
}
```

### Mark-and-sweep по шагам

1. **Mark** — пройти по графу объектов от корней, пометить достижимые.
2. **Sweep** — пройти по всем объектам и освободить непомеченные.
3. **Compact** (опционально, в V8 есть) — уплотнить память, чтобы избежать фрагментации.

В V8 — несколько поколений: *young generation* (Scavenger, часто), *old generation* (Mark-Compact, реже). Объекты, пережившие несколько сборок, «продвигаются» в старшее поколение. Поэтому долгоживущие объекты дешевле в обслуживании, а короткоживущие — часто и дорого.

### Tri-color marking (для ответа «глубоко»)

- **White** — ещё не посещён (кандидат на удаление).
- **Grey** — известен как достижимый, но дети ещё не обработаны.
- **Black** — достижимый и его дети обработаны.

Инкрементальная сборка может прерваться; для сохранения корректности используют **write barrier** (если во время сборки создали ссылку — её нужно отметить).

### Слабые ссылки

```js
const cache = new WeakMap(); // не мешает удалению ключа
const ref = new WeakRef(target); // может дать undefined после GC
const registry = new FinalizationRegistry((k) => console.log("освобождён", k));
```

Такие коллекции участвуют в достижимости **условно**: ключ `WeakMap` не считается удерживаемым, если на него больше нет других ссылок.

### Утечки: что на самом деле удерживает память

1. Глобальные переменные, «случайно» созданные (без `let` в sloppy-режиме, `window.x = ...`).
2. Таймеры и обработчики без снятия.
3. Подписки на события с `{ signal }` без `abort()`.
4. DOM-узлы, удалённые из документа, но живущие в переменной.
5. Замыкания с большими данными.
6. Кэши без ограничения размера (нужен LRU или `WeakRef`-ключи).
7. `Map`/`Set` вместо `WeakMap`/`WeakSet` в кэшах объектов.

### Чем проверить

- **Chrome DevTools → Memory**: Heap snapshot (сравнить два снимка), Allocation instrumentation on timeline, Performance Monitor.
- **`performance.measureUserAgentSpecificMemory()`** — экспериментально.
- В Node: `--inspect`, `process.memoryUsage()`.

### Что часто спрашивают

- **«Можно ли освободить память вручную?»** — Нет. Управляемая память: только убрать ссылки и включить `WeakMap`. `delete` — только удаление свойства.
- **«Когда GC запускается?»** — Не детерминированно: по достижению порогов и эвристик (heap limit, заполнение young generation).
- **«Утечка — это что?»** — Объект, который *больше не должен* использоваться, но остаётся достижимым. GC не может понять «должен», он видит только ссылки.

> [!warning] Важная фраза
> «GC в JS не использует reference counting, поэтому циклические ссылки не утечка сами по себе. Утечка — это достижимость, которой не должно быть».
