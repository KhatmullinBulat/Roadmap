# Мутировать состояние в Pinia

## Краткий ответ (30 секунд)

В Pinia **можно** менять `state` напрямую (`store.count++`, `store.items.push(...)`) — в отличие от Vuex, где обязательны мутации. Pinia отслеживает изменения через реактивность Vue, поэтому devtools и подписки работают. Но **принято** держать изменения в **actions**: там валидация, побочные эффекты, батчинг, единая точка для тестов и devtools. Риски хаотичных мутаций: логика расползается по компонентам, сложно отследить, неочевидные взаимные зависимости, тесты и отладка тяжелее, отсутствие «транзакционности» (`$patch`).

## Подробно

### Разрешено

```ts
const cart = useCartStore();
cart.items = [];          // замена
cart.count++;             // прямое изменение
```

### Рекомендуется

```ts
// store
function clear() {
  items.value = [];
  log("cart:clear");
}

// компонент
cart.clear();
```

- Action — имя для операции, её можно найти/протестировать/вызвать из нескольких мест.
- Внутри — всё, что касается инвариантов: не позволить отрицательное количество, валидация.

### `$patch`

```ts
store.$patch({ count: 1, items: [] });
store.$patch((state) => { state.count = 1; });
```

- Одно обновление (меньше подписок/рендеров) и одна запись в devtools.

### Почему в Vuex было иначе

- **Vuex**: `state` менять только через `mutations` (синхронные), `actions` (async) коммитят мутации; `strict: true` ловит прямые мутации.
- **Pinia**: «store = composable», типизация проще, нет отдельных mutations. Отсюда вопрос «можно ли напрямую» — можно, но не нужно.

### Риски хаотичных мутаций

1. **Неявная связность**: поле A меняется в 5 компонентах — непонятно, откуда баг.
2. **Дублирование логики** (валидация в двух местах, разная).
3. **Нет единой точки для логов/аналитики**.
4. **Тесты**: тестировать функцию проще, чем «последовательность мутаций в компонентах».
5. **Порядок обновлений / гонки**: два действия в разных компонентах могут перетереть результат.
6. **SSR**: мутация в модуле вне запроса — утечка между пользователями.

### Приватные данные

- Не добавляйте в `state` то, что должно быть локальным (флаг открытия модалки) — это увеличивает глобальный «кэш» и ререндеры.
- Для «внутренних» вычислений — замыкание в setup-стор (не возвращать из `defineStore`).

### Плагины и подписки

```ts
cart.$subscribe((mutation, state) => {
  localStorage.setItem("cart", JSON.stringify(state));
});
```

- Работают и при прямых мутациях, и при actions; но `$patch` объединяет в одну запись.

### Что ответит интервьюеру

> «Технически можно, и Pinia это поддержит. Но я держу изменения в actions как в API стора: там инварианты, логирование, batch. Прямые мутации — для тривиального локального изменения в компоненте, который владеет этим состоянием, либо для `$patch`».
