# Почему чистый CSR хуже для SEO

## Краткий ответ (30 секунд)

CSR отдаёт поисковику **почти пустой HTML**: `<div id="app"></div>` и `<script>`. Контент появляется только после скачивания и выполнения JS. Google умеет рендерить JS, но это **отложенная очередь**, «rendering budget», и не гарантия для всех краулеров; соцсети/мессенджеры (OG-теги) и большинство сторонних ботов JS не выполняют. Итого: риск нестабильной индексации, медленный первый контент (LCP), нет метаданных для шаринга. SSR/SSG отдают контент и мету сразу — индексируются надёжнее и быстрее. Но **SEO — не единственная причина**: Core Web Vitals и UX тоже страдают без HTML.

## Подробно

### Что видит бот

```http
GET /product/42
→ 200 OK, Content-Type: text/html

<!doctype html>
<html>
  <head><title>Магазин</title></head>
  <body><div id="app"></div><script type="module" src="/assets/index.js"></script></body>
</html>
```

Без выполнения JS страница — пустой каркас.

### Почему «Google умеет JS» — не решение

- Рендер JS — вторая, отложенная фаза индексации (может занимать дни), тратит ресурсы.
- Бюджет краулинга ограничен — большие сайты рискуют не проиндексировать часть.
- **Other bots**: Bing (рендерит частично, хуже), соцсети и мессенджеры (Open Graph), SEO-аудиты, AI-краулеры, парсеры сниппетов — часто без JS.
- Ошибка в бандле = пустая страница для бота.
- SPA с client-side navigation не отдаёт «страницы» вовсе — каждая ссылка ведёт в тот же HTML.

### Метаданные

- `title`, `description`, `canonical`, `og:image`, `hreflang` — должны быть в **исходном HTML**.
- В CSR их приходится ставить JS (`useHead` выполнится, но для краулера-без-JS это поздно).
- Для соцсетей SSR — практически обязателен.

### Скорость

- CSR: браузер должен скачать JS, выполнить, сделать запрос данных, только потом отрисовать → высокий LCP.
- SSR/SSG: HTML с контентом + preload критичных ресурсов → LCP ниже.
- Core Web Vitals влияют на UX, а UX учитывается в ранжировании сильнее контента, но всё же как фактор.

### Что делать, если обязательно CSR

1. **Prerender** статических маршрутов (SSG хотя бы для маркетинга).
2. **Pre-render / dynamic rendering** для ботов (edge-прокси, отдающий HTML боту) — так делали для Google до улучшений, сейчас чаще SSR.
3. **Валидные HTML-снимки**: `<noscript>`-контент, `title`/мета в `index.html` локально (по умолчанию).
4. **Внутренняя навигация** — нормальные `<a href>` (история/back) через router link.
5. **Sitemap.xml**, `robots.txt`, `canonical`.
6. **OG-теги для шаринга** — через SSR-эндпоинт/лейаут на сервере, хотя бы для публичных страниц.

### Nuxt

- `ssr: true` по умолчанию, SSR отдаёт HTML.
- `routeRules` — CSR только для приватных разделов.
- `useSeoMeta`/`useHead` работают на сервере — теги в HTML.

> [!warning] Подвох
> «Google видит SPА, значит SEO не проблема?» — видит, но не гарантированно, с задержкой и не все боты. И первый контент может быть очень поздним. Для контента/конверсии — SSR/SSG.
