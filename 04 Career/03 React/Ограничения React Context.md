# Ограничения React Context

## Краткий ответ (30 секунд)

Context решает проблему «прокидывания пропсов через много уровней», но это **не** полноценный state manager. Ограничения: 1) любое изменение `value` ререндерит **все** компоненты-потребители (нет селекторов); 2) `value` сравнивается по ссылке — новый объект каждый рендер = перерендер всех; 3) нельзя обновлять `value` без ререндера обёртки-провайдера; 4) в одной иерархии можно читать только ближайший провайдер (вложенные — перекрывают); 5) для частых обновлений (курсор, ввод, таймер) — неподходящая производительность; 6) сложная логика мутаций → reducer или внешний стор; 7) SSR/тестирование — нужны явные провайдеры в тестовой обвязке.

## Подробно

### 1. Все потребители ререндерятся

```jsx
const StoreContext = createContext(null);

function StoreProvider({ children }) {
  const [state, setState] = useState({ users: [], theme: "light" });
  const value = useMemo(() => ({ state, setState }), [state]);
  return <StoreContext.Provider value={value}>{children}</StoreContext.Provider>;
}

// Любой setState → новый value → все useStore перерендерились,
// даже если их часть данных не изменилась
```

Селекторов в контексте нет — `useContext` возвращает всё значение. Обходные пути:
- **Разделить контексты** по частоте изменений (theme vs data vs actions);
- **Разделить state и dispatch**: `dispatch` стабилен, и компоненты, которым нужен только dispatch, не перерендерятся;
- Передать в контекст «шину» с подписками (`subscribe`, `useSyncExternalStore`), как в Zustand.

### 2. Ссылочная стабильность `value`

```jsx
// ❌ новый объект каждый ререндер Provider
<Ctx.Provider value={{ user, logout }}>
```

Нужен `useMemo`/`useCallback` или постоянная ссылка:

```jsx
const value = useMemo(() => ({ user, logout }), [user, logout]);
```

### 3. Обновление = ререндер провайдера

`setState` живёт в провайдере, поэтому вся поддерево передаётся в `children`. `children` в React «стабильны» (элемент создан выше), поэтому глубокие «не-потребители» не перерендерятся — и это одно из главных преимуществ. Но `Provider` всё равно перерендерится.

### 4. Ближайший провайдер

```jsx
<Theme.Provider value="dark">
  <Theme.Provider value="light">
    <Child /> {/* получит "light" */}
  </Theme.Provider>
</Theme.Provider>
```

Ожидание «оба» неверно: `useContext` возвращает ближайшее значение. Для двух тем в одном дереве нужны разные контексты.

### 5. Частые обновления

Курсор, drag, ввод, "наведение на каждую строку" — context раздувается. Тогда:
- подписка на элемент/строку через колбэк + `useState` в строке;
- `useSyncExternalStore` для точной подписки;
- CSS `:hover` вместо JS-состояния.

### 6. Нет devtools и структуры

Context — «связка», а не стор: нет истории, devtools, middleware, серверной синхронизации. Для бизнес-логики — Redux Toolkit/Zustand/RTK Query, либо хук + reducer.

### 7. Тесты и SSR

Каждый потребитель должен оказаться внутри провайдера. В тестах часто оборачивают `render` в набор провайдеров (`test-utils`), в SSR — оборачивать приложение на сервере.

### Когда контекст — правильный выбор

- **Тема, локаль, авторизация**, настройки — редко меняются.
- **`dispatch`/клиент API** — стабильная ссылка.
- **Композиция UI** — «издатель-подписчик», не частое состояние.
- Внутри компонентной библиотеки (Tabs, RadioGroup).

### Сравнение

| | Context | Zustand/Redux | Props |
|---|---|---|---|
| Селекторы | нет | да | — |
| Devtools | нет | да | — |
| Частые обновления | плохо | хорошо | плохо при глубокой передаче |
| Простота | высокая | средняя | высокая |
| Ререндер | все потребители | только подписанные | только дети |

> [!tip] Как отвечать
> «Context — это DI, а не стейт-менеджер. Любое изменение value ререндерит всех потребителей, селекторов нет. Помогает разделение контекстов, стабилизация value и `dispatch` отдельно. Для частых обновлений — внешний стор с `useSyncExternalStore`».
